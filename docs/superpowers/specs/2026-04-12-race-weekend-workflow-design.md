# Race Weekend Workflow — Design Spec

## Overview

Restructure the Strategy page into a three-phase race weekend workflow:
**Practice Lab → Strategy Builder → Race Plan.** The Practice Lab provides
light coaching guidance and tracks readiness. The Strategy Builder shows
parameters gathered from practice with override capability. The Race Plan
shows the computed output with statistics. A separate Input Analysis view
correlates driving style with fuel and tire consumption.

The hard coaching (detailed technique analysis, video review, corner-by-corner
breakdowns) lives on the webapp — the desktop app provides light, actionable
nudges during practice and lets the user know when they have enough data to
build a reliable strategy.

## Design Principles

- **Light coaching, not a driving school.** Brief status messages, not essays.
  "Braking consistency: 78% — run 5 more laps" not "Your braking technique
  in turn 3 shows late application with insufficient trail braking..."
- **Auto-capture everything.** The user drives. The app watches. No buttons
  to start/stop recording during practice.
- **Show readiness, not raw data.** "Soft compound: READY (18 laps, high
  confidence)" not "fuel_per_lap: 2.81, wear_per_lap: 3.2, estimated_life: 18"
- **Defer to the webapp for deep analysis.** The desktop app says "see detailed
  corner analysis on lap-coach.racing" with a link/export.

## Phase 1: Practice Lab

### What it replaces

The current "Record Stint" button + manual compound selection. Instead,
practice data capture is fully automatic.

### Auto-Capture Logic

When the app detects a practice or qualifying session (from `session_type`):
1. **StintRecorder starts automatically** — no button press needed
2. **Compound detection** — from sim telemetry if available (iRacing, ACC),
   otherwise inferred from tire temp behavior or user tags it after
3. **Stint boundaries** — detected automatically from pit stops
   (is_in_pits transitions). Each pit-to-pit run is one stint.
4. **Pit measurements** — captured automatically on every pit stop
5. **Per-lap data** — times, temps, fuel deltas all logged per lap

Readiness % is computed from model availability:
- Thermal model available = +25%
- Warmup model available = +25%
- Degradation model available = +25%
- Confidence "high" (30+ laps) = +25%
- Each factor is 0% or 25% — simple, clear, no partial credit

#### Light Coaching Nudges

A small card below readiness showing 1-3 actionable suggestions:

```
┌─ SUGGESTED NEXT STEPS ────────────────────────────┐
│                                                    │
│  → Run 12 more laps on softs for high confidence   │
│  → Do a full stint on mediums (currently 0 stints) │
│  → Try a pit stop to measure pit time              │
│                                                    │
└────────────────────────────────────────────────────┘
```

The nudges come from analyzing what's missing:
- No compound data at all → "Run at least 10 laps on [compound]"
- Compound has laps but no warmup model → "Do 3 full stints (pit-to-pit)"
- No pit profile → "Do a pit stop to measure pit lane time"
- Confidence is "low" → "Run N more laps for reliable data"
- All compounds ready → "You're race-ready! Head to Build Strategy →"

These are generated by a pure function: `compute_practice_nudges(profiles, pit_profile) -> list[str]`

#### Input vs Consumption Card

Shows the correlation between driving style and resource usage:

```
┌─ INPUT → CONSUMPTION ─────────────────────────────┐
│                                                    │
│  Throttle aggressiveness:  72%  → fuel +0.15 L/lap │
│  Trail braking intensity:  High → wear +0.8%/lap   │
│  Cornering smoothness:     68%  → wear +0.3%/lap   │
│                                                    │
│  ⚡ Lifting 5% earlier in S2 would save ~0.1 L/lap │
│                                                    │
└────────────────────────────────────────────────────┘
```

This requires correlating per-lap input metrics (from `LiveInputDiagnosticsTracker`)
with per-lap fuel deltas and tire wear (from `StintRecorder`). The correlation
is computed by a new function:

```python
def correlate_inputs_consumption(
    input_snapshots: list[dict],   # per-lap input metrics
    fuel_deltas: list[float],      # per-lap fuel consumption
    wear_rates: list[float],       # per-lap tire wear
) -> list[InputCorrelation]
```

`InputCorrelation` is a simple dataclass:
```python
@dataclass
class InputCorrelation:
    input_name: str          # "Throttle aggressiveness"
    input_value: float       # 0-100 percentage
    fuel_impact_l: float     # additional L/lap vs baseline
    wear_impact_pct: float   # additional %/lap vs baseline
    suggestion: str | None   # actionable tip, or None
```

The baseline is the best (most efficient) lap — correlations are relative
to that. The suggestion is generated only when the impact is significant
(>0.05 L/lap or >0.5%/lap wear).

## Phase 2: Strategy Builder

### Entry Point

User clicks the **BUILD** tab (or a prominent "Build Strategy →" button
on the Practice tab when readiness is sufficient).

```
│  Mode:  ○ LAP RACE  ● TIMED RACE                  │
│                                                    │

│  Fuel capacity   110 L           AUTO from sim     │
```

Only race duration/laps is user-editable. Everything else shows where the

### Entry Point

Generated when user clicks "Process Strategy" on the Build tab. Also
auto-generated when entering a race session if a strategy was built.

### Statistics Card

```

│                                                    │
│  Estimated laps       42                           │
│  Estimated race time  1:03:18                      │
│  Pit stops            1                            │
│                                                    │
│  Qualifying target    1:42.3  (based on soft pace) │
│  Race pace target     1:43.1  (stint average)      │
│                                                    │
│  Best case            1:01:45  (clean, no SC)      │
│  Expected             1:03:18  (with warmup costs) │
│  Worst case           1:06:22  (+10% degradation)  │
│                                                    │
│  Fuel margin          +3.2 L at finish             │
│  Tire grip at finish  52% (comfortable)            │
└────────────────────────────────────────────────────┘
```

Best/expected/worst case is not Monte Carlo (that's Sub-Project B).
For now: expected = optimizer output, best = no warmup penalty + min
fuel curve, worst = +10% wear + +5% fuel + warmup.

### Strategy Timeline (existing, enhanced)

The colored stint timeline bar already exists. Keep it. Add:
- Weather overlay (rain probability mapped to laps) when iRacing
- Warmup penalty markers on first 3 laps of each stint
- Fuel level curve below the timeline

### Stint Detail Table (existing, enhanced)

Already exists. Add columns:
- Warmup cost (seconds lost to cold tires in this stint)
- Fuel to add (from pit profile: varies per stop)
- Pit time (computed per stop, not flat)

### Override Capability

Every value in the Race Plan is overridable:
- Click a stint → edit its length
- Click pit time → override with a manual value
- "Recalculate" button re-runs optimizer with overrides locked

### Live Race Integration (existing)

Already built — when a race session starts:
- Plan goes live
- Auto-recalculates from actual consumption
- Divergence alerts surface
- Weather changes trigger re-plan
- The compact overlay shows the same data

- "Build Strategy →" button on Practice tab switches to Build tab
- "Process Strategy" button on Build tab switches to Race Plan tab

## Auto-Capture Wiring

Currently, stint recording requires pressing "Record Stint" and picking
a compound. Change this:

### In `StrategyViewModel`:

Add method `on_session_detected(session_type, track, car)`:
- If session_type is practice/qualifying: auto-start StintRecorder
- Compound: default to "unknown", tagged when user specifies or sim provides

Add method `on_pit_detected()`:
- Called when `is_in_pits` goes True → finalize current stint, start new one
- Each pit-to-pit run becomes one StintRecord automatically

Add method `on_session_ended()`:
- Finalize any active stint recording
- Refresh profiles

### In `DesktopService` or `SessionCoordinator`:

Wire `snapshot_changed` to feed snapshots to `StrategyViewModel.update_live()`.
Wire session lifecycle events to `on_session_detected` / `on_session_ended`.

## Out of Scope

- Hard coaching (corner-by-corner technique, video replay, reference laps) — webapp
- Monte Carlo simulation for best/worst case — Sub-Project B
- Competitor strategy prediction — Sub-Project C
- Automatic compound detection from tire temperature signatures (nice-to-have, later)
- Drill system with specific exercises ("do 5 laps lifting early in T3") — webapp
- Export/link to webapp for detailed analysis
